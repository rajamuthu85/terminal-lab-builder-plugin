# Interactive Terminal Lab Builder

This skill packages the architecture and build pipeline used to create the "Linux Terminal Lab" — a single-file, self-contained HTML artifact that simulates real terminal sessions across multiple environments (RHEL, SUSE, Ubuntu, Debian, and two-node clusters), with commands that actually mutate a live, stateful world (disks, LVM, Btrfs, RAID, mounts, cluster resources), plus a companion "Self-Study" page that auto-annotates every command in the catalog. Use it to reproduce the same quality of interactive lab for a **different platform or technology** — Windows/PowerShell, a cloud CLI (AWS/Azure/GCP), Docker/Kubernetes, a database shell (psql/mysql/mongosh), network gear (Cisco IOS/JunOS), git, or anything else with a command-line surface worth teaching.

Do not just write static "terminal transcripts." The defining property of this kind of lab is that commands are **live**: creating a volume group in one command makes it show up in `vgs`/`lsblk` three commands later, exactly like a real system. Anything less is a worse product than what this skill produces.

## When NOT to use this

If the user just wants a cheatsheet, a static reference page, or a slide deck of commands, this is overkill — use a doc or the pptx/Slides flow instead. This skill is for when the user wants something people actually *practice on*.

## High-level architecture

One published Artifact (`Artifact` tool, or an equivalent self-contained HTML delivery), built from source files in a scratch workspace and assembled by a build script — never hand-author the final HTML directly, because the sample outputs must be generated by actually running the simulated commands (see Phase 4). The finished page has exactly two top-level pages, switchable by tabs:

1. **Terminal Lab page** — an environment/lab picker (dropdown, not tabs — a dropdown scales to many environments without UI clutter), a large left-hand terminal pane (most of the screen — this is what students stare at), and a right-hand reference panel with two tabs: **Commands** (the full categorized catalog for the selected lab, searchable, with a "Try it" button that runs the command for you) and **Details** (full explanation + real sample output +, for generated hands-on-lab commands, a "Run lab steps up to here" button that replays every earlier step in that category so the student can jump into the middle of a procedure).
2. **Self-Study page** — independent of any single lab: a category sidebar, a search box, and a scrollable list of cards, one per unique command in the *entire* catalog, each rendered as a color-coded breakdown (base command / subcommand / option / argument / shell operator) with a plain-English explanation for every single part. This is generated automatically (Phase 5), never hand-written per command — hand-writing thousands of explanations does not scale and drifts out of sync.

Never add a separate "disks" tab, a separate "guided labs" tab, or a flashcard deck tab — those were tried and explicitly rejected in favor of folding hands-on procedures directly into the Commands catalog as generated categories (see Phase 3) and folding storage state into ordinary inspection commands (`lsblk`, `df`, `pvs`, etc.) that a student would run anyway. Keep the surface area to exactly the two pages above unless the user asks for something else.

## Phase 1 — Scope the catalog

For the target platform(s)/environment(s), decide:

- The list of distinct "labs" (environments) — e.g. for a cloud-CLI version this might be AWS/Azure/GCP/multi-cloud; for a database version, psql/mysql/mongosh. Each lab gets its own hostname/prompt identity and its own command catalog.
- A **shared catalog** of commands common to all labs (analogous to `common.txt`), plus a **per-lab catalog** of environment-specific commands.
- A flat category taxonomy per lab (`# Category Name` headers) covering the full breadth of the platform — aim for the same density as the original (roughly 300 commands per lab before generated hands-on categories are added).
- Any "free resources" a hands-on module needs to feel real. In the Linux lab this was "2 empty disks" per environment so LVM/RAID/Btrfs labs are practicable. Find the analogous thing for the new platform (e.g. two empty S3 buckets, two unattached EBS volumes, a spare git remote, two idle Kubernetes nodes) and provision it into the base state of every lab.

Write the catalog as plain-text, pipe-delimited rows, one file per lab plus one shared file:

```
# Category Name
command ~~ one-line description ~~ sample_output_or_blank
another command ~~ description ~~ 
```

Leave `sample_output` blank for anything whose real output should come from the live engine (Phase 4 fills these in automatically) rather than hand-typing it — hand-typed sample output silently drifts out of sync with engine behavior and is the single biggest source of bugs in this style of project.

## Phase 2 — Design the live-state engine

This is the core of what makes the lab "real" rather than a canned transcript. Build a single `engine.js` exposing `createEngine(LABS)` that returns `{ labs, run(lab, cmdline), reset(lab), H, ... }`.

1. **Model the domain's real stateful objects** as a plain JS state tree per lab instance (e.g. `lab.disk` for Linux storage: `blk` (raw block devices), `md` (RAID arrays), `lvs` (logical volumes), `vgs`, `pvs`, `btr` (btrfs filesystems), `mounts`). For a new platform, find the equivalent — e.g. for a Kubernetes lab: namespaces, pods, deployments, services, PVCs as nested objects with real relationships; for a cloud CLI: a fake account with regions, VPCs, instances, buckets, IAM roles.
2. **Write uniform accessor helpers early** for anything addressable through more than one underlying map — e.g. this project's `bdev(lab,k)` / `bsize(lab,k)` / `bpath(lab,k)` which resolve a device key across `blk`, `md`, and `lvs` uniformly. Skipping this and reaching into one specific map directly (`D.blk[d].size`) is exactly the bug class that caused the worst production incident in this project (a crash whenever Btrfs was built on an LVM volume or RAID array instead of a raw disk — a combination a human tester would rarely think to try but a combinatorial matrix test caught immediately). Build the equivalent uniform accessors for the new domain's cross-referenced state up front.
3. **Command dispatch**: maintain a `MUT` set (or equivalent) of command bases that must be intercepted for stateful handling (anything that changes state or whose output depends on current state), and a dispatcher function that pattern-matches the command line and computes real output from current state *before* falling through to the static catalog (exact match, then fuzzy match) for purely informational commands whose output never changes.
4. **Fail loudly, never silently.** Wrap the top-level `run()` call site (in the UI layer) in try/catch and surface `[lab] Internal simulator error while running this command: <message>. Press Reset lab if the lab looks inconsistent.` — log to console too. A silent failure in a stateful simulator is indistinguishable from "the feature doesn't work" and will get reported as a product bug, not an engine bug — so it must be impossible to fail silently.
5. **Give failures actionable hints.** When a command fails for a state-dependent reason (wrong device type, missing prerequisite step, wrong resource state), append a specific hint with the exact remediation command(s) — e.g. this project's `mountHint()` which tells the student the exact `pvcreate`/`vgcreate`/`lvcreate`/`mkfs` sequence needed when they try to mount a device that was never formatted. This is what turns "the tool told me no" into "the tool taught me the right sequence."
6. **Persistence semantics**: decide what survives a reset vs. what's part of the base scenario (e.g. `/etc/fstab` entries persisting across `mount -a`, or a cluster resource surviving a simulated node failover) and implement it explicitly — don't let it be accidental.

## Phase 3 — Generate the hands-on-lab categories

Write a small generator module (analogous to `storage_cat.py`) that returns, per lab, a list of realistic multi-step procedures as ordinary catalog rows tagged `gen: true` (with an expected return code), inserted as their own categories (e.g. "Storage Lab 1" .. "Storage Lab 5") at the *front* of that lab's catalog so they can't be missed. Each step's `sample_output` is left `None`/blank — it is filled from the real engine, never hand-written (Phase 4). Order steps so each is a valid precondition for the next (e.g. never reuse a disk across two volume groups without a "remove from old VG" step first) — a build-time assertion that the generated step count matches the target is worth adding.

For the new platform, this is where the "free resources" from Phase 1 get exercised: e.g. for Kubernetes, generated categories walking through creating a namespace, a deployment, scaling it, a rolling update, and a rollback, using the two idle spare nodes; for a cloud CLI, provisioning and tearing down real resource dependency chains.

## Phase 4 — Build pipeline (`build.py` + `fillouts.js`)

`build.py` (or equivalent):
1. Parses all catalog files, dedupes, and proportionally trims the shared-catalog portion (never the per-lab or generated portions) to hit each lab's target command count.
2. Prepends the Phase-3 generated categories (de-duped against anything already in the static catalog with the same normalized command text).
3. Emits `labs.json` (the row data) and substitutes the engine code, UI code, and data into a `template.html` skeleton at fixed markers (e.g. `/*__DATA__*/`, `/*__ENGINE__*/`, `/*__UI__*/`).
4. Runs a Node script (`fillouts.js`) that spins up the *real* engine, resets each lab, and executes every single catalog row's command through it in catalog order, capturing actual output for any row whose sample output was left blank, and asserting the actual return code matches the row's expected `rc`. This is what guarantees the reference deck can never silently drift from simulator behavior — treat any assertion failure here as build-breaking, not a warning.
5. Rewrites `labs.json` with the filled-in outputs and re-substitutes into the final HTML.

This two-pass structure (write catalog rows with blank outputs → run them for real → bake real outputs back in) is the single most important pattern in this skill. It is what separates "transcript that looks plausible" from "transcript that is provably accurate," and it should be reproduced exactly for any new platform.

## Phase 5 — Self-Study explainer generator

Build a layered, data-driven knowledge base rather than hand-writing an explanation per command (there will be 1,000+ unique commands across all labs):

- Base description per top-level command/binary.
- Subcommand description for multi-level tools (anything with a verb-like second token: `pcs resource create`, `kubectl rollout restart`, `aws s3 cp`).
- Per-flag/option description (short and long forms).
- Positional-argument meaning per command (what does the 2nd bare word after `cp` mean vs. the 2nd bare word after `chmod`), plus a generic `key=value` parameter-meaning table for anything that takes `option=value` style parameters.
- A tokenizer/classifier (`explainCommand(cmd)`) that walks an arbitrary command line — handling quotes, `$(...)`, shell operators (`| || && ; > >> < 2>&1`), bundled short flags, longest-match subcommand detection — and renders every token as a color-coded, labeled, explained part, falling back to a heuristic classifier for anything not explicitly catalogued (never leave a token unexplained; a generic-but-present explanation beats a blank).

After writing this, build a coverage-check script that runs `explainCommand` over every row in every lab's final catalog and reports any command/option that still falls through to the generic fallback. Iterate until residual generic fallbacks are a handful at most (this project got 4,817 rows across 1,426 unique commands down to 3 residual generic-fallback argument instances) — this is a required step, not optional polish.

## Phase 6 — UI

- Two top-level pages (Terminal Lab / Self-Study) via a simple page-switcher, not nested inside the lab picker.
- Terminal Lab page: environment dropdown up top, big terminal on the left (majority of viewport width on desktop), Commands/Details tabs on the right. A history buffer, up/down-arrow recall, and a visible "Reset lab" action are table stakes.
- Self-Study page: category sidebar + search box + card list with "show N more" pagination (don't render 1,000+ cards at once) and a "Try it" button on each card that switches to the Terminal Lab page and actually runs that command.
- Accessible ARIA roles throughout (tablist/tab/tabpanel, listbox/option, live regions for terminal output).
- Light/dark theme via CSS custom properties on `:root`, with a `@media (prefers-color-scheme: dark)` block guarded by `:root:not([data-theme="light"])` plus an explicit `:root[data-theme="dark"]` override for a manual toggle.
- `localStorage` (wrapped in try/catch) only for trivial per-viewer prefs like font size — never for lab state.

## Phase 7 — Testing discipline (do not skip, do not shortcut)

This project's hardest bug (a crash specifically when Btrfs was built on an LVM volume or RAID array — a scenario a human tester is unlikely to think to try) was found only by combinatorial testing, not by manual spot checks. Reproduce this discipline for any new platform:

1. **Full-catalog smoke test**: run every row's command through a fresh engine instance per lab; flag exceptions, "not found"/fuzzy-match fallbacks that shouldn't have been needed, unresolved template placeholders, and return codes that don't match expectations.
2. **Natural-order flow test**: run each lab's full catalog in category order end-to-end and confirm no step depends on state a later step hasn't created yet.
3. **Combinatorial matrix test**: identify every *path* to a given piece of state (e.g., for storage: raw disk vs. three different partitioning tools vs. plain LVM vs. LVM-across-two-disks vs. software RAID) crossed with every downstream option (every filesystem type, every mount-point style, every command invocation form), and test all combinations, not just the "happy path" combination. For the Linux lab this was 6 labs × 7 device-creation paths × 5 filesystems × 5 mount styles × 5 invocation forms = 4,500 scenarios, each independently asserting consistency across every inspection command that should reflect the change (`df`/`findmnt`/`mount`/`lsblk` all agreeing, and a written file surviving unmount/remount). Design the equivalent cross-product for the new domain's stateful surface before declaring anything fixed.
4. **Real-browser validation**: after the automated suite passes, load the actual built HTML in a real browser (Playwright) and hand-type at least a few complete realistic flows across every lab, checking the terminal output for the expected success text and confirming zero page/console errors. Automated engine tests alone are not sufficient sign-off — the UI wiring is a separate failure surface.
5. Treat "validate and fix" requests from the user as license to build whatever automated test harness is needed to find the *actual* root cause before touching code — this project's fixes were only trustworthy once matrix + browser testing both passed at 100%.

## Phase 8 — Publish

- Publish via the `Artifact` tool as a single self-contained HTML file (inline all CSS/JS; no external hosts except Google Fonts, since Artifact-published pages block other external hosts).
- On every subsequent revision, republish to the *same* artifact URL with a short, specific label describing what changed and how it was validated (e.g. "Mount fixes, validated on 4,500 scenarios") — never publish a fresh URL for an iteration of the same lab.
- If the session is attached to a Project relevant to the topic, keep a synced copy of the built HTML as a project doc so future sessions have it as a starting point.

## Adapting to a genuinely new platform — checklist

When asked to build this for a new platform, treat it as redoing Phases 1–8 for that domain, not reusing any Linux-specific code:

- [ ] New catalog content (shared + per-lab), same pipe-delimited format and category-header convention
- [ ] New state-object model in the engine reflecting that platform's real stateful primitives
- [ ] New `MUT`/dispatcher command list and new hint functions for that platform's failure modes
- [ ] New generated hands-on-lab categories exercising that platform's "free resources"
- [ ] Re-run the fillouts pass so sample outputs are real, not hand-typed
- [ ] New/extended args knowledge base for the Self-Study explainer, re-run the coverage check
- [ ] Re-run the full testing ladder (smoke → flow → combinatorial matrix → real-browser) before publishing
- [ ] Rebrand UI copy/labels/theme for the new platform; keep the two-page architecture (Terminal Lab / Self-Study) unless the user asks otherwise
